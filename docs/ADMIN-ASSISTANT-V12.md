# Península v1.2 — admin assistant and deployment

This release extends the complete v1.1 codebase. It keeps the five public pages in three languages, SEO metadata, public enquiry concierge, group matching, WhatsApp handoff, inbox and existing private calendar. No real services have been provisioned or connected. Use a dedicated Península Supabase project, never QuoteCore+.

## 1. Demo before credentials

Node 22. Extract the ZIP to a project folder. Run `npm install`, then create `.env.local` containing:

```
PENINSULA_DEMO_MODE=true
SITE_INDEXABLE=false
```

Run `npm run dev`; open `http://localhost:3000/admin`. Select **Entrar (demo)**. The three tabs are Agenda, Mensajes, Ajustes. The assistant is a button within the panel, not a fourth tab. Demo mode uses sample records only; changes are stored in browser-local storage, not a server. If storage is blocked, the current session is in-memory. Settings has a reset-demo button. No real customer records or credentials should be used in this mode. On a protected Vercel preview, set the same environment flags and leave database/OpenAI credentials unset if doing demo-only testing. Demo is disabled in Vercel Production and when SITE_INDEXABLE=true. Do not expose a demo on the final public site. The public enquiry assistant still requires configured APIs; its existing fallback remains. The separately supplied standalone HTML is an illustrative interactive implementation using the shared deterministic modules, not a compiled React application or an API test.

Try the example `Añade una clase mañana de 09:00 a 11:00 para 4 personas`. Inspect the proposed event, discard it, then retry and confirm. `¿Qué tengo en la agenda hoy?` is read-only. In demo mode the parser supports explicit dates or hoy/mañana with 24-hour HH:mm times; broader phrasing requires the real model. Demo voice uses the browser's optional dictation service (which may process audio remotely), or device keyboard dictation; it is not the OpenAI audio integration. No voice data is automatically submitted as an instruction. The app's actual microphone workflow requires HTTPS (or localhost), microphone permission and MediaRecorder support. Live audio is capped at 45 seconds and 3 MB; keyboard dictation or typing is always available.

## 3. Owner assistant behavior and safety

One owner-only chat uses the same branding and OpenAI account as the public concierge but a separate capability boundary. The model can return a typed intent (create, edit, delete, read, clarify). It has no database write tool. The backend supplies a bounded set of calendar events (not raw customer messages, contact details or credentials); event titles and owner utterances may contain personal data, so use short non-sensitive notes and approve the privacy/data-handling policy. Public concierge still sees only owner-approved group opportunities. All times interpreted in America/Santo_Domingo. Relative dates are anchored to local today. A single event operation at a time; ambiguous dates/target/time should prompt clarification. Bulk changes, automatic price/booking commitments, messaging and settings changes are not supported by this assistant. Permanent working-hour/weekend rules remain in Ajustes. Enquiry-to-booking / join-existing-group remains in Mensajes with manual confirmation.

Voice recordings are captured only after the mic button is pressed, uploaded to the authenticated admin endpoint for transcription, then returned as editable text. Recording or transcription alone does not send a chat message. Server validates size/type and rate limits. Raw audio is not retained by our application. OpenAI processing/retention terms still apply; Responses requests set store:false, which is not a guarantee of zero retention. Actual browser microphone compatibility, audio transcription and privacy notice need approval/testing.

The proposal endpoint validates types, local time, range and group fields, creates a server-held proposal with ten-minute expiry, and returns an exact summary including before/after and overlapping blocks. Confirm button or explicit typed `Confirmar` sends only the proposal ID, not model-generated writes or editable action payload. Owner authentication and same-origin enforcement are required. The database RPC locks, checks owner and expiry, revalidates the original row and overlap snapshot, and applies the single change atomically. Duplicate confirmations return the recorded result, not a second event. Stale changes are refused and a new proposal is required. Linked reservations cannot be silently deleted or reclassified as non-lessons by the assistant. Cancelling the UI proposal clears it locally; expired server records are cleaned during usage checks. Normal manual calendar edits remain available. The owner can explicitly confirm a known overlap; new overlaps after preview invalidate it. No assistant changes are made by AI without human approval. Public API cannot invoke this workflow.

## 4. Acceptance tests (must pass on preview)

1. Test demo login without credentials, reset and logout. No network request to Supabase/OpenAI from demo admin. Verify demo disabled in production and no real data appears in demo. Try invalid login and non-owner login in real mode; unauthenticated admin GET/POST/multipart must reject. Check origin and direct RPC grants. Verify session refresh and logout.
2. In real mode use typed Spanish commands: create a lesson tomorrow 09:00–11:00, block a busy period, read schedule, edit a specific event, delete a standalone block. Confirm exact dates, time zone and type. A request missing date/end or identifying multiple events must ask for clarification. Read and proposal must not mutate calendar. Discard must not mutate. Confirm button and typed Confirmar should work exactly once; expired proposal, changed target, new overlap, forged ID and another owner's request must fail. Test linked booking safeguards and existing group capacity transaction.
3. Dictate on iPhone Safari, Android Chrome, iPad and MacBook Safari/Chrome; inspect editable transcript, deny microphone, cancel recording, hit 45-second cap, simulate API failure. Verify no silent submit or calendar write. Use keyboard dictation as fallback.
4. Check the three tabs, 44px+ touch targets, bottom navigation, no horizontal overflow, manual event creation, schedule settings, inbox and booking workflow on real devices. Verify confirmation panel is not covered by fixed navigation. Test offline and free-tier Supabase pause: preserve public direct WhatsApp fallback and display a clear error rather than claiming a save.
5. Test public concierge in EN/ES/FR, approve exact final message, confirm saved copy, verify WhatsApp opens on customer device (customer presses Send), alternate email/phone path, group matching excludes private/unavailable/unsuitable/full groups. Ensure messages contain no invented prices and no promises. Test all 15 public routes, SEO metadata, sitemap and robots, contact details and original video/branding.
6. Review knowledge base and factual content with Cristian later; do not claim a model has been trained. Obtain media/font permissions and privacy/terms covering enquiry storage and AI/audio. Confirm retention/export/deletion policy. Keep production indexing disabled until approved.
