# v1.5 — fast confirmations and installable admin

Baseline: supplied live repository archive `peninsula-surf-v1.4-9b16772.zip` (commit `9b16772`). No dependencies added, no SQL migration, no new credentials. Preserve any deployment fixes after that commit. The public pages, enquiry mode toggle, SEO, data and existing authenticated proposal RPC are retained.

## Deploy

1. Create a branch from the currently deployed branch. Review and apply `Peninsula_v15_Update.patch` with `git apply --check` first; merge conflicts manually, do not overwrite current env configuration. The full ZIP is an alternative for a clean checkout, not an instruction to replace live files.
2. `npm ci`, `npm test`, `npm run typecheck`, `npm run build`. Node 22 recommended. Deploy to a protected Vercel preview using the existing Supabase and OpenAI configuration. No migration needed; v1.2–1.4 SQL must already be installed.
3. The uploaded v1.4 code included a server-side quick login using configured owner credentials. v1.5 disables that endpoint and UI on production/indexable sites. Use a real owner login for production. Keep quick login disabled unless local/protected preview, and never expose an unprotected preview with owner quick login. Revoke/rotate any credentials if the old shortcut was publicly accessible; inspect access logs. Demo mode stays isolated to fictional browser-local data.
4. Verify with the real owner on a phone/tablet, then merge into production. Do not reset or alter any real records as part of deployment.

## Public assistant

The configured OpenAI model interprets natural language and returns a structured draft, FAQ category, short follow-up and finish preference. A useful draft can be reviewed immediately. After two customer turns, a known service or meaningful enquiry is enough to review even if preferences are missing. The customer may continue refining or asking questions. No forced format, duration, exact time, name, or location. Missing preferences are omitted, not invented. Approved FAQs remain deterministic; no prices or binding availability.

The review shows the exact prepared message, optional duration chips, response expectation, and the clear privacy/approval notice. Confirm button or a standalone typed affirmative submits the displayed message through existing `/api/concierge/submit` validation. A customer may choose the non-WhatsApp route and enter one valid email or international phone; no contact details needed for WhatsApp. On successful save, the WhatsApp URL opens in the same browsing context (avoids async popup blocking); the customer still presses Send. A direct link remains on the saved screen if the browser returns to it. No claim of WhatsApp delivery. Direct contact and simple form are retained, and errors retain the typed enquiry.

Compatible group matching stays limited to explicitly shareable lessons with sufficient capacity and owner-approved ability. Prefer requested time/duration when dates are equally close. Never reserve seats or quote a discount. Group acceptance records interest, not submission. Date corrections may trigger another matching attempt. Quick reply chips for date/level/quantity use the normal interpretation endpoint where matching may be relevant; duration chips and group decision update the draft locally.

## Private assistant

Propose first, execute only using the existing authenticated confirmation endpoint and stored proposal ID. Standalone affirmative text (yes, yeah, proceed, confirmed, etc.; ES equivalents) and Confirm button call the same handler. Conditional or corrective replies are not approvals; a recorded voice note only proposes, never commits. Voice transcription auto-submits for interpretation, not execution. On a normal creation the start and kind are enough; default end is computed in code. Defaults (minutes): lesson 120; busy 60; rest 480; travel 120; unavailable 60; available 120. Explicit end wins. Moves without an end preserve previous duration. Date/time shortcuts and editable proposal fields allow corrections without another LLM call; Review updated times issues a new authenticated validated proposal, invalidating the previous one. Confirm that new proposal explicitly; overlap warnings recompute. Notes, locations, participants, and group metadata are optional. No automatic opening of groups. Linked booking deletion remains restricted to manual calendar workflow. Existing overlap snapshot, expiry, idempotency and owner verification RPC remain unchanged.

## Admin PWA

`/admin` has its own manifest, title, viewport, Apple touch icon, 192/512 branded PNGs and standalone display. `AdminInstall` registers the network-only `/admin-sw.js` with scope `/admin`; no calendar data, enquiries, credentials or private API responses stored in Cache Storage. The offline page is generic. This is an online-first PWA, not an offline scheduling system. Home screen install does not bypass authentication. Chrome/Android install prompt where supported; iOS/iPadOS Safari Share → Add to Home Screen. macOS Safari Add to Dock / Chrome Install where supported. The three tabs and existing bottom navigation remain. Test secure HTTPS context and mic permissions on real devices (including installed app).
