# Península v1.1 — enquiry concierge and owner dashboard

## Approved operating model
The public site is a conversational enquiry engine, not a reservation system. Cristian retains control of pricing, timing, ocean safety, availability, group combinations and confirmation. WhatsApp is the final handoff and normal human conversation; there is no WhatsApp Business Platform API, no automatic send, and no WhatsApp inbox synchronization. The customer must press Send in WhatsApp. An enquiry submitted without WhatsApp requires a phone or email. On the WhatsApp path contact details are optional; an enquiry without contact information is not actionable until the customer actually sends the WhatsApp message. The app labels this accurately. The same reference and approved message appear in the private inbox and the click-to-chat draft. A direct WhatsApp option remains for accessibility and when the AI/database is unavailable.

## Architecture
- `src/components/Enquiry.tsx`: chat modal; optional simple form fallback, contact selection, exact message preview, consent and explicit submission. Contact fields collected separately from LLM requests. Warn customers not to enter contact details in the chat; free text may still contain personal data.
- `src/app/api/concierge/route.ts`: server-only OpenAI Responses call. The model extracts structured fields and classifies an FAQ; the server chooses approved FAQ copy, missing fields and compatible group dates. No browsing, arbitrary tool calls, database credentials, raw private calendar or booking authority available to the model. It is prompted, not fine-tuned. Schema adherence is not factual accuracy; review/evaluate extraction on real samples.
- `src/lib/concierge.ts`: multilingual allowed FAQ answers, matching rules and deterministic final-message rendering. Match only shareable lessons, adequate declared spare capacity, compatible level, dates in an explicit window up to 14 days or one day either side of the requested date. Only future lessons in next 32 days are considered. Suggest at most once per chat; date/time are leads, not availability promises. Open spots are owner-entered; no hold is made on enquiry. If customer wants private, no group is suggested. Rough dates are retained; if not resolvable, no calendar suggestion is made.
- `src/app/api/concierge/submit/route.ts`: validates channel and contact, reconstructs exact message and compares with approved preview; idempotent save with UUID, reads current response status, optional email notification. No model calls during final save. No fake “sent” state.
- `/admin`: Agenda (today-first, week toggle), Mensajes, Ajustes. Large touch targets, recurring response hours, slower weekend toggle, events: lesson, busy, unavailable, travel, rest, available. Time zone America/Santo_Domingo. A manually available block can override recurring hours but never a concurrent teaching/away block. Owner adds/edits lesson, toggles open group and spare places/level. Confirm enquiry to create a new lesson or join an existing open group, in one SQL transaction. Group confirmation decrements spare places. Cancellation or deletion requires reviewing the linked enquiries and manually adjusting spare places if necessary; full cancellation/rebooking workflow is not implemented. Owner can add multi-day time blocks for holidays. Secure HTTP-only access/refresh cookies and owner-ID check; verify refresh/logout on real devices. Add to Home Screen using browser shortcut; full standalone PWA/offline support is not implemented.
- `supabase/upgrade-v11.sql`: use on a dedicated project only; first run `schema.sql` if fresh. Grants restricted to server role, RLS enabled. For existing v1.0 use backup and upgrade SQL once. Do not run against QuoteCore+.

## Setup
1. Create separate Supabase project, disable public signups, create owner through dashboard, copy owner UUID. Run base schema then upgrade in SQL editor. Review migrations in a nonproduction project before applying. The app uses a project-wide service-role credential only within the dedicated project; never expose it in public env variables. Verify anon and authenticated nonowner cannot read any data or call RPCs.
2. Create a dedicated OpenAI API project and key with billing enabled, configure `OPENAI_API_KEY` and `OPENAI_MODEL=gpt-5.4-mini` in Vercel server env. Confirm model access; API billing separate from ChatGPT. This implementation expects Responses API structured outputs and `reasoning.effort: none`. No API key in git. The SQL guard allows 16 turns per 10 minutes per fingerprint and 300 per rolling 24h globally. Chat history is capped at eight customer turns and 1,000 characters each. Model output cap 600 tokens. These are application caps, not a guaranteed currency cap. Configure API usage alerts and monitor actual consumption; consider Vercel firewall/bot protection before public launch.
3. Set Supabase vars and production origin using `.env.example`; optional Resend notification to owner. Keep `SITE_INDEXABLE=false` until approved. `npm install`, `npm test`, `npm run typecheck`, `npm run build`, deploy a protected preview, validate security before accepting real personal data.
4. Privacy: explain AI processing before chat, contact details saved only after approval, how to delete records, provider handling and retention. `store:false` requests no model application-state storage; standard API abuse-monitoring logs may still apply. Keep chat transcript transient in browser; no full conversation is saved to Supabase. Define a retention/deletion policy with owner and test deletion. Do not claim zero retention. Current simple consent text is not a complete privacy policy.
5. If Supabase pauses or OpenAI fails, use fallback simple form or direct WhatsApp; do not show success if save fails. Enable optional email for inbox-only alerts; owner must check inbox if disabled. A browser home-screen shortcut is enough initially.
