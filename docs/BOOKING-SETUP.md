# v1.0 — booking and SEO deployment

This is an implementation candidate, not a provisioned production system. The v0.9 visual design remains the baseline. New pages, the form and the dashboard are source code. The local availability unit test passes; Next.js installation/build and real database/API/browser integration must be verified by the deployment agent. Do not enable public enquiries until the checks below pass and the owner approves privacy wording. No secret keys or live accounts are included.

## 1. Supabase (private database and authentication)

- Create a dedicated Supabase project. Run `supabase/schema.sql` in its SQL editor once. It creates `enquiries`, `calendar_blocks`, `operating_hours`, and the short-lived hashed rate-limit table, plus a service-role-only atomic insert RPC. RLS is enabled and anon/authenticated have no table access. Enable Data API for `public`. The server uses legacy JWT-format anon and service_role keys for this REST implementation; do not use publishable/secret replacements without changing the auth headers appropriately.
- In Authentication > Users, create Cristian's owner account, verify his email, use a strong unique password, disable public sign-ups, and copy his user UUID. Configure auth rate limits. Review password recovery with owner; no self-service reset is implemented in v1.0.
- Set server variables in Vercel / `.env.local`: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `ADMIN_USER_ID`. Do not use `NEXT_PUBLIC_` for any of these. The service role bypasses RLS and must never be committed. Admin requests verify the access token with Supabase and compare its owner UUID; the cookie is HttpOnly, SameSite=Strict, Secure in production, expires in up to one hour (sign-in again required). No signup route. Keep preview protected. Consider MFA or managed auth before wider release.
- Optional: configure `RESEND_API_KEY`, `ENQUIRY_EMAIL_FROM` (verified sender), `ENQUIRY_EMAIL_TO` (owner), and `NEXT_PUBLIC_SITE_URL` to receive a simple notification email for each saved request. This email contains no customer data. If notification fails, the enquiry remains in the dashboard; no guaranteed push delivery or retries in this release.
- Visit `/admin` (Spanish UI chosen for Cristian). Enter the actual working hours and days; defaults shown in form are suggestions only until saved. No default business schedule is assumed. Dates are Dominican local time; server records UTC. Add, edit and delete calendar blocks. Week view currently uses 2,000 calendar rows and 500 recent enquiries; implement paging/archiving if needed. Calendar is manually managed, no Google Calendar integration yet.

## 2. Enquiry behaviour

Website CTAs open a translated modal with service, name, international WhatsApp number, preferred date/time, duration, group size, experience and notes (only relevant fields for purchase/clothing). Explicit permission is requested to share these details for this enquiry. The form POSTs to `/api/enquiries`; a successful DB insert returns a reference and the current status, evaluated at submission, not at the requested lesson time. The confirmation then offers a WhatsApp link including the enquiry reference and details. The customer must tap Send in WhatsApp; opening a link does not send a message. The owner receives the saved request in the dashboard independently, and can tap WhatsApp to reply. On DB/configuration failure there is no false success; direct WhatsApp remains available. Public endpoint returns only coarse status, never calendar contents. Raw phone/name are not sent to email. The rate limit is five submissions per ten minutes per hashed IP; the honeypot is supplementary. Verify trusted proxy IP headers on Vercel and consider CAPTCHA/WAF, abuse monitoring and idempotency before public release. Separate actual booking from enquiry: Cristian manually agrees price, location, date/time, creates a linked calendar event and marks the request confirmed. Overlaps prompt a warning, not a hard block. Do not show exact private dates or locations in automated replies. Overlap precedence: off > travel > lesson > rest > configured hours. Unknown status yields neutral reply. No automatic booking, price, conditions or board stock promise.

## 4. SEO / release

- 15 public page/language routes: home, boards, clothing, beginner lessons, rental. All have translated metadata and links. New pages are directly linked from home/services and boards/rent, footer and each other. Each page has distinct copy. Canonical/hreflang, sitemap, robots, and basic SportsActivityLocation JSON-LD use configured HTTPS origin. Verify the actual business address/phone and image before indexing. No invented coordinates, hours, ratings, prices. Search metadata is not a ranking guarantee.
- `NEXT_PUBLIC_SITE_URL` = approved canonical HTTPS domain. `SITE_INDEXABLE=false` by default, only true on approved production (Vercel preview also noindex). Preview protection is recommended; robots is not access control. Verify headers/meta and sitemap; root redirects to `/en`, legacy `/index.html` permanent redirect. Original ZIP also contained privacy.html and terms.html; archived under docs/legacy-for-review, not deployed. Update these for actual data use, privacy, retention and legal terms, restore old URLs or redirect to their matching new pages before domain cutover. Do not send them to an unrelated homepage. Verify all indexed legacy URLs in Search Console and redirect each appropriately. 
- Create/claim Google Business Profile, confirm location and contact, submit sitemap, verify hreflang/canonicals, add social image and test Core Web Vitals. No conversion tracking yet; track enquiry creation and WhatsApp clicks separately once privacy configuration approved.
